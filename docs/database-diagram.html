The central architectural rule is dependency direction: infrastructure calls the application and domain layers. The domain never imports SQLAlchemy, FastAPI, Plaid, or AWS libraries.

Notes:

  • domain/models.py defines facts and accounting records; it performs no I/O.
  • domain/ledger.py decides what journals a lifecycle event should create.
  • providers/base.py describes what normalized provider data looks like to Ledge.
  • providers/fake.py supplies repeatable pages without credentials or networking.
  • persistence/repository.py locks rows, invokes domain factories, stages database rows, flushes drafts, and seals journals. Its caller owns commit or rollback.
  • api/app.py wires one configured user identity, the async session factory, and the health, account, transaction, and sync-status routers.

Transaction is the provider’s latest complete fact. TransactionRemoval is smaller because providers only identify which transaction disappeared. Ledge loads the last-known amount, description, and active journal from PostgreSQL.

Current lifecycle execution

sequenceDiagram
    participant Caller
    participant Repository as LedgerRepository
    participant Domain as Domain factories
    participant ORM as SQLAlchemy session
    participant DB as PostgreSQL

    Caller->>ORM: begin transaction
    Caller->>Repository: add / modify / remove
    Repository->>DB: lock current projection when needed
    Repository->>Domain: create journal and/or reversal
    Domain-->>Repository: immutable balanced JournalEntry
    Repository->>ORM: add draft journal and postings
    Repository->>DB: first flush
    Note over Repository,DB: Rows exist only inside the open transaction
    Repository->>ORM: set sealed_at
    Repository->>DB: second flush
    DB->>DB: validate posting count and zero balance
    DB-->>Repository: accept or raise
    Repository-->>Caller: return Ledge transaction UUID
    Caller->>DB: commit on success; rollback on exception

Lifecycle effects

flowchart LR
    add[Added event] --> original[Append original journal]
    original --> active[Projection is active]

    modify[Modified event] --> reverse_old[Reverse active journal]
    reverse_old --> replacement[Append replacement journal]
    replacement --> update[Update active projection]

    remove[Removed identity] --> load[Load last-known projection]
    load --> reverse_current[Reverse active journal]
    reverse_current --> removed[Mark projection removed]
  • Addition creates one current financial effect.
  • Modification preserves the old entry, cancels it, and appends the new effect.
  • Removal preserves everything, cancels the current effect, and changes status.
  • Repeating an identical event does not append another financial effect.

        UUID user_id FK

        VARCHAR description

        VARCHAR status
        TIMESTAMPTZ created_at
        TIMESTAMPTZ updated_at

    JOURNAL_ENTRIES {
        UUID id PK
        UUID external_transaction_id FK
        UUID reversal_of_entry_id FK
        VARCHAR description
        TIMESTAMPTZ created_at
        TIMESTAMPTZ sealed_at
    }

    POSTINGS {
        BIGINT id PK
        UUID journal_entry_id FK
        SMALLINT line_number
        VARCHAR ledger_account
        BIGINT amount_cents
    }

Table roles:

  • users is the current ownership boundary and the future authentication subject.
  • transaction_sync_states remembers one provider connection’s committed cursor.
  • financial_accounts represents checking, savings, and credit accounts.
  • external_transactions is mutable current provider truth, not ledger history.
  • journal_entries is immutable accounting history after sealing.
  • postings contains ordered debit and credit lines in integer cents.
  • There is intentionally no ledger_states table. PostgreSQL replaces the large in-memory snapshot as durable state.

Database protections

flowchart TB
    python[Domain balance validation]
    draft[Unsealed journal draft]
    postings[Insert two or more postings]
    seal[Set sealed_at]
    trigger[PostgreSQL sealing trigger]
    immutable[Immutable journal and postings]

    python --> draft --> postings --> seal --> trigger
    trigger --> count{At least two postings?}
    count -- yes --> balance{Amounts sum to zero?}
    balance -- yes --> immutable
  • Composite foreign keys prevent cross-user account ownership mistakes.
  • (user_id, provider_transaction_id) prevents duplicate provider identities.
  • A journal cannot reverse itself or a journal belonging to another transaction.
  • An original journal can be reversed at most once.
  • Sealing triggers independently verify posting count and balance.
  • Sealed journals and postings cannot be updated or deleted.
  • Foreign-key deletes use RESTRICT, preserving audit history.

TransactionSynchronizer now starts from a stored cursor, asks TransactionProvider for every available page, and only then opens one database transaction to apply all changes and advance the cursor. If any lifecycle operation fails, both ledger changes and cursor advancement roll back. FastAPI now reads user-scoped accounts, current transactions, and committed sync progress through async SQLAlchemy sessions. The next boundary is safe event intake that can hand work to this existing pipeline.
