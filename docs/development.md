# Development guide

This is the detailed operating guide for developing and testing Ledge. The root
README stays product-facing; implementation explanations and local workflows live
under `docs/`.

## Requirements

- Python 3.12 or newer
- Docker with Docker Compose for the local PostgreSQL instances

Docker runs only PostgreSQL. The Python application and tests run from the local
virtual environment.

## Environment setup

```bash
python -m venv venv
venv/bin/pip install -e '.[dev]'
docker compose up -d postgres
```

Configure the application, disposable test database, and current single-user
identity:

```bash
export LEDGE_DATABASE_URL='postgresql+psycopg://ledge:ledge_local@localhost:5432/ledge'
export LEDGE_TEST_DATABASE_URL='postgresql+psycopg://ledge:ledge_local@localhost:5432/ledge_test'
export LEDGE_USER_ID='11111111-1111-1111-1111-111111111111'
```

The credentials in `compose.yaml` are development-only values. `.env.example`
documents the variables while `.env` remains ignored.

## Database migrations

SQLAlchemy models describe the schema expected by the current Python application.
Alembic migrations describe how an existing PostgreSQL database reaches that
schema one version at a time. Developers must update both when a schema change is
intentional.

Install every migration:

```bash
venv/bin/alembic upgrade head
```

Create a candidate migration after changing SQLAlchemy metadata:

```bash
venv/bin/alembic revision --autogenerate -m "describe the schema change"
```

Autogeneration is a draft, not a substitute for review. Read both `upgrade()` and
`downgrade()`, verify backfills and constraint ordering, then run the migration
tests. The suite uses `alembic check` to reject drift between models and the
migration head.

## Tests

Run everything:

```bash
venv/bin/pytest
```

Run only tests that do not require PostgreSQL:

```bash
venv/bin/pytest -m 'not integration'
```

Run only PostgreSQL integration tests:

```bash
venv/bin/pytest -m integration -vv
```

Show the first complete traceback and local variables while debugging:

```bash
venv/bin/pytest -vv -x --tb=long --showlocals
```

Use `pytest.raises` when a failure is expected. Pytest normally captures that
exception because raising it is the passing behavior. Temporarily remove the
context manager or run the underlying code directly when you want to inspect its
uncaught traceback.

Run coverage:

```bash
venv/bin/pytest --cov=src --cov-report=term-missing
```

Current verified checkpoint: 145 passing tests and 94% statement coverage across
`src/`. Treat this as a dated repository measurement that must be rerun before it
is used in a resume or project description.

## Static checks

```bash
venv/bin/ruff check .
venv/bin/ruff format --check .
```

Ruff can format changed Python files with:

```bash
venv/bin/ruff format .
```

## Run the API

After PostgreSQL is running and migrations are installed:

```bash
venv/bin/uvicorn api.app:create_app --factory --reload
```

Useful URLs and routes:

```text
http://127.0.0.1:8000/docs
GET  /health
GET  /accounts
GET  /transactions?status=active&limit=10&offset=0
GET  /sync-status
POST /webhooks/transactions
```

An empty list is valid when the development database has not been seeded for the
configured user. The normalized webhook also requires a matching
`transaction_sync_states` row; otherwise it correctly returns `404`.

## Repository map

```text
src/domain/          immutable values, invariants, and ledger decisions
src/persistence/     SQLAlchemy models, event intake, and repository writes
src/providers/       provider-owned interface and deterministic fake adapter
src/application/     cursor synchronization and leased event processing
src/api/             FastAPI wiring, reads, and normalized webhook intake

migrations/versions/ ordered PostgreSQL schema and trigger history

tests/domain/        fast pure-Python behavior
tests/persistence/   real PostgreSQL constraints and repository transactions
tests/providers/     provider contract and fixture behavior
tests/application/   synchronization, rollback, leases, and concurrency
tests/api/           ASGI behavior and user-scoped PostgreSQL queries
tests/scenarios/     complete in-memory transaction lifecycle
```

## Generated and local-only files

The following are expected development artifacts and should not be committed:

- `venv/`: local Python environment
- `__pycache__/` and `*.pyc`: Python bytecode caches
- `.pytest_cache/` and `.ruff_cache/`: tool caches
- `.coverage` and `htmlcov/`: local coverage results
- `*.egg-info/`: package metadata generated by editable installation
- `.env`: local configuration and secrets

An `.egg-info` directory is metadata used by Python packaging tools to record the
installed project name, version, dependencies, and source files. It is generated
from `pyproject.toml`; it is not application source.

## Commit boundaries

Keep commits focused on one coherent behavior. Database changes normally include
the model, reviewed Alembic migration, and tests in one feature commit. Use
Conventional Commit subjects such as:

```text
feat(sync): add durable event processing leases
docs: refresh project architecture
test(repository): cover failed pending replacement
```
